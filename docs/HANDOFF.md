# 이어서 작업하기

다른 환경(집 PC 등)에서 이 프로젝트를 이어받을 때 먼저 읽는 문서.
저장소를 클론한 뒤 이 파일부터 확인하면 현재 상태와 다음 작업을 파악할 수 있다.

---

## 0. 이 문서를 읽는 AI에게 — 작업 방식

**이 프로젝트는 결과물보다 학습이 목적이다.** 아래 규칙을 지킬 것.

1. **혼자 만들지 말 것.** 한 번에 한 조각씩 진행한다.
   순서는 `무엇을 왜 만드는지 설명` → `동의 확인` → `파일 1~2개 작성` → `사용자가 직접 실행` → `커밋`.
   여러 파일을 한꺼번에 만들어 완성본으로 건네지 않는다.

2. **코드보다 설계가 먼저다.** 선택지가 여럿인 판단은 코드를 쓰기 전에 정하고 `docs/설계결정.md`에 기록한다.

3. **사용자가 겪지 않은 경험을 사용자의 것으로 서술하지 말 것.**
   AI가 발견한 문제를 "직접 만들어보니 알았다" 식으로 문서나 답변 스크립트에 넣지 않는다.

4. **커밋 단위는 조각 하나.** 커밋 메시지는 영어로 작성한다.

5. **틀렸거나 모르는 것은 즉시 말할 것.** 확인 없이 단정하지 않는다.

6. **사용자 환경에서 실행되는 것만 "확인됐다"고 한다.** AI 환경에서 돌아간 것은 참고일 뿐이다.

## 1. 프로젝트 개요

자동창고(AS/RS)에서 반출된 물품이 컨베이어를 거쳐 소터로 분류되기까지의 제어 흐름 구현.
상위 시스템(WMS)과 설비(PLC) 사이에서 WCS가 담당하는 역할을 코드로 확인하는 것이 목적이다.

```
랙 로케이션 → 스태커크레인 → P&D 스테이션 → 반출 컨베이어 → 소터 → 슈트
              └────────── WCS 담당 구간 ──────────┘
```

| 문서 | 내용 |
|---|---|
| `README.md` | 범위 · 구조 · 동작 방식. Mermaid 다이어그램 포함 |
| `docs/설계결정.md` | ADR. 선택지가 여럿이었던 판단 7건과 근거 |
| `docs/HANDOFF.md` | 이 문서 |

**설계 판단은 전부 `docs/설계결정.md`에 있다.** 구현 방향이 헷갈리면 거기부터 볼 것.

## 3. 환경

| 항목 | 값 |
|---|---|
| OS | Windows |
| 에디터 | Cursor |
| JDK | Temurin 17 |
| 빌드 | Gradle Wrapper (`gradlew`). **Gradle 전역 설치 없음** |
| 패키지 | `io.github.hhhjbot.wcs` |

Maven은 설치돼 있지 않다. `mvn` 명령을 안내하지 말 것.

### 클론 후 첫 실행

```powershell
git clone https://github.com/hhhj-bot/wcs-poc.git
cd wcs-poc
./gradlew test
```

첫 실행 시 Gradle 배포판을 내려받으므로 몇 분 걸린다.

Gradle 없이 규칙만 확인하려면:

```powershell
javac -encoding UTF-8 -d out src\main\java\io\github\hhhjbot\wcs\domain\TaskStatus.java
javac -encoding UTF-8 -cp out -d out tools\TaskStatusCheck.java
java -Dfile.encoding=UTF-8 -cp out TaskStatusCheck
```

### git 계정 주의

전역 git 설정이 회사 계정으로 되어 있어, 저장소마다 개인 계정을 지정해야 한다.

```powershell
git config user.name "이름"
git config user.email "개인메일"
git config user.email          # 확인 후 진행
```

`--global` 없이 저장소 안에서 실행할 것. 커밋 후 `git log --format="A: %ae | C: %ce"` 로 한 번 더 확인한다.

## 5. 다음 작업 — `LocationCode`

### 무엇

랙 주소 문자열을 좌표로 분해하고, 담당 스태커크레인을 결정한다.

```
A-01-03-02  →  zone=A, aisle=1, bay=3, level=2  →  담당 크레인 SC-A01
```

### 왜

스태커크레인은 통로마다 한 대씩 배치된다. 따라서 로케이션 주소만 알면 어느 설비가 이 작업을 수행할지가 결정된다.
설비 배정 로직을 별도로 두지 않고 주소에서 유도하는 이유가 이것이다.

### 고려할 점

- 입출고 스테이션은 랙 좌표가 없다. 별도 표현이 필요하다
- 형식이 어긋난 문자열은 예외로 거부한다
- 프레임워크 의존성 없이 작성한다. `java.*` 만 사용

## 6. 연계 작업 — mfg-systems-ui

별도 저장소(React + Vite + TypeScript)에서 진행 예정인 작업.

### NextjsPage → ProgrammingPage 개편

기존 Next.js 소개 페이지를 **Programming** 페이지로 확장하고 언어·스택별 섹션으로 나눈다.

- Next.js 섹션 — 기존 내용 유지
- **Java 섹션 신규** — 개념 설명 + 이 저장소 링크 + 코드 일부 노출

### 시뮬레이션 페이지

이 저장소에서는 다루지 않는 **물품 이동 애니메이션**을 React로 구현한다.
파렛트가 랙에서 나와 크레인·P&D·컨베이어를 거쳐 슈트로 배출되는 과정, 만재 시 재순환까지 시각화한다.

역할 분담이 정해져 있다(ADR-0006).

| | 담당 |
|---|---|
| 이 저장소 | 태그·상태를 확인하는 계기판. 정적 HTML + 폴링 |
| mfg-systems-ui | 설명을 위한 시각화. 파렛트 이동 애니메이션 |

**착수 시점은 이 저장소의 6단계(소터) 이후.** 내용이 확정되기 전에 만들면 두 번 작업하게 된다.
