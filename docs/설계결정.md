## ADR-0001 · 범위를 출고측 설비 연결 구간으로 한정

### 결정
랙 로케이션 → 스태커크레인 → P&D 스테이션 → 반출 컨베이어 → 소터 → 슈트 구간을 대상으로 한다.
입고측(컨베이어 → 프로파일 체크 → 크레인 → 랙)은 이후 과제로 둔다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 자동창고 단독 | 설비가 하나면 조율 대상이 없어 제어 계층의 역할이 드러나지 않는다 |
| 차량 시스템(AGV/AMR) | 경로 계획·교통관제·충전 스케줄이 얽혀 범위 통제가 어렵다 |
| 피킹 시스템 | 상위 시스템 영역에 가까워 제어 계층 학습이라는 목적에 맞지 않는다 |
| 입고측 연결 구간 | 성립하지만 판단 로직이 출고측보다 적다 |

### 근거
설비 간 물품 인계가 발생해야 조율 로직이 필요해진다. 크레인·컨베이어·소터가 이어지는 구간이 이에 해당한다.
분류 처리에는 목적지 결정이 포함되므로 단순 반송보다 다룰 사항이 많다.

### 영향
설비 간 인수인계가 핵심 과제가 된다. 핸드셰이크를 형식이 아니라 필요에 의해 구현하게 된다.

## ADR-0002 · 설비 점유 시 거절 대신 대기열 사용

### 결정
설비별 대기열을 두고, 설비가 가용해지면 순차 하달한다. 진행 중인 작업이 있다는 이유로 신규 작업을 거절하지 않는다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 인터록으로 차단 후 재시도에 위임 | 구현은 단순하나 컨베이어에 이미 투입된 물품은 회수할 수 없다 |
| 조건 없이 하달 | 진행 중 작업의 명령 태그를 덮어써 오배송 또는 완료 신호 유실이 발생한다 |

### 근거
크레인 1대가 동시에 1건만 처리한다는 제약은 사실이나, 그에 대한 대응은 거절이 아니라 순서화다.
상위에서 수신한 지시는 폐기하지 않고 큐에 보관한다.

### 영향
하달 순서를 결정하는 기준이 필요해진다. 해당 기준은 ADR-0005에서 정의한다.

## ADR-0003 · 슈트 배정은 WMS 계획 + WCS 우회

### 결정
출고지시에 WMS가 결정한 슈트(`plannedChute`)를 포함한다.
WCS는 이를 따르되, 만재 또는 장애 시 대체 슈트로 우회하고 실제 배출 슈트(`actualChute`)를 함께 기록한다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| WMS 전담 지정 | 만재 발생 시 WCS가 대응할 수단이 없어 재순환 후 리젝트로 귀결된다 |
| WCS 전담 배정 | WMS가 물품의 행선지를 알 수 없어 출하 실적 집계와 사전 적재 계획이 어렵다 |

### 근거
계획 수립에 필요한 정보(주문·출하·배차)는 WMS가, 실시간 상태 정보(슈트 만재·설비 장애)는 WCS가 보유한다.
각 계층이 보유한 정보 범위에 맞춰 책임을 배분한다.

### 영향
계획 슈트와 실제 슈트의 차이가 기록으로 남는다. 우회 빈도는 배차 계획 또는 상차 지연을 역추적하는 지표로 활용할 수 있다.

## ADR-0004 · 리딩 실패 시 라인을 정지하지 않음

### 결정
바코드 리딩에 실패한 물품(no-read)은 리젝트 슈트로 즉시 배출한다. 후속 처리는 작업자가 수행한다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 수동 입력 대기 | 라인이 정지한다. 단건 처리를 위해 전체 처리량을 희생하는 구조가 된다 |
| 재순환 후 재리딩 | 라벨 훼손·오염이 원인인 경우가 대부분이라 결과가 동일하다. 루프만 점유한다 |

### 근거
리딩 실패의 원인은 대부분 물리적 요인이며 소프트웨어 재시도로 해소되지 않는다.
라인 외부로 신속히 배출해 작업자가 처리하는 편이 전체 처리량에 유리하다.

### 영향
리젝트 슈트는 예외 처리 전용으로 예약한다. 재순환 횟수 초과분도 동일 슈트로 배출한다.

## ADR-0005 · 차량·컷오프는 슈트 속성 수준까지만

### 결정
슈트에 도크 번호, 차량, 컷오프 시각을 속성으로 부여한다.
주문·출하건·배차 자체는 관리하지 않으며, 웨이브 운영은 범위에서 제외한다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 차량 정보 미포함 | 슈트 번호의 출처가 설명되지 않는다. 대기열이 선입선출 외의 기준을 가질 수 없다 |
| 배차·웨이브까지 관리 | 배차는 상위 시스템의 영역이며, 상태 관리 증가로 제어 계층 구현이라는 목적이 희석된다 |

### 근거
슈트는 최종 목적지가 아니라 상차 직전 단계이며, 슈트 번호는 배차 계획에서 결정된다.
차량 출발 시각을 속성으로 보유하면 작업 우선순위 기준을 정의할 수 있다.

### 영향
- 대기열 정렬 기준이 선입선출에서 컷오프 임박 순으로 변경된다 (ADR-0002의 후속 결정)
- 슈트 만재의 원인을 상차 지연으로 해석할 수 있다
- 슈트 수량이 동시 처리 가능한 배송 경로 수의 상한이 된다는 사실만 반영하고, 해소 방안(웨이브)은 다루지 않는다

## ADR-0006 · 화면은 정적 HTML + 폴링

### 결정
설비 상태 모니터는 정적 HTML과 JavaScript 폴링으로 구성한다. 서버사이드 템플릿은 사용하지 않는다.
물품 이동 시각화는 이 저장소가 아닌 별도 프론트엔드 프로젝트에서 다룬다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| JSP 등 서버사이드 템플릿 | 설비 상태가 수백 ms 단위로 변경되므로 요청 시점 렌더링 방식과 맞지 않는다 |
| SPA 프레임워크 도입 | 상태 모니터 단일 화면을 위해 빌드 체인을 추가할 필요가 없다 |

### 근거
이 저장소의 화면은 태그와 상태를 확인하는 용도로 한정한다. 설명을 위한 시각화는 목적이 달라 도구를 분리한다.

### 영향
서버 측 의존성이 증가하지 않는다. 시각화 요구가 발생해도 이 저장소의 구조에 영향을 주지 않는다.

## ADR-0007 · 문서는 저장소 내 마크다운 + Mermaid

### 결정
설계 문서를 저장소 안에 마크다운으로 둔다. 다이어그램은 Mermaid 문법으로 작성해 코드 블록에 포함한다.
선택지가 여럿이었던 판단은 이 ADR 문서에 누적한다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 이미지 파일(PNG·drawio) 첨부 | 변경 내역이 diff로 확인되지 않는다. 원본 파일과 내보낸 이미지의 동기화가 어긋난다 |
| 외부 위키·노션 | 코드와 별도 위치에 있어 함께 갱신되지 않는다. 저장소만 받은 사람은 설계를 볼 수 없다 |
| 문서 없이 코드 주석만 | 선택하지 않은 대안이 기록되지 않는다. 왜 그 구조인지 추적할 수 없다 |

### 근거
다이어그램이 텍스트이면 변경 내역이 리뷰 대상이 되고, 코드 수정과 같은 커밋에서 함께 갱신할 수 있다.
GitHub과 주요 IDE가 Mermaid를 기본 렌더링하므로 별도 도구나 빌드 단계가 필요하지 않다.

### 구성

| 문서 | 내용 |
|---|---|
| `README.md` | 범위 · 구조 · 동작 방식. 다이어그램 포함 |
| `docs/설계결정.md` | 선택지가 여럿이었던 판단과 근거 |

사용 중인 다이어그램 유형:

| 유형 | 용도 |
|---|---|
| `flowchart` | 설비 구성과 물품 흐름 |
| `sequenceDiagram` | WCS와 PLC 간 신호 교환 순서 |
| `stateDiagram-v2` | 작업 상태 전이 규칙 |

### 영향
- 다이어그램 수정이 코드 리뷰 대상에 포함된다
- 렌더링은 뷰어(GitHub·IDE) 지원에 의존한다. 지원하지 않는 환경에서는 코드 블록으로 표시된다
- 노드 수가 많은 복잡한 도면에는 적합하지 않다. 그 경우 별도 도구로 작성해 이미지로 첨부한다

## ADR-0008 · 보관 단위를 케이스로 한다 (미니로드 AS/RS)

### 결정
보관·반송 단위를 **케이스**로 하고, 자동창고를 **미니로드 AS/RS**로 잡는다.
설비 구성은 스태커크레인 · 반출 컨베이어 · 소터 세 종을 유지한다.

### 배경
소터는 물품을 슈트로 배출하는 설비이므로 파렛트를 다루지 못한다.
파렛트를 보관 단위로 두면 소터 앞에서 케이스로 전환하는 공정이 반드시 필요해진다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 파렛트 유지 + 디팔레타이저 추가 | 설비가 넷으로 늘고, 단위 전환이라는 별도 개념이 추가된다 |
| 파렛트 유지 + 피킹 스테이션 추가 | 주문별 필요 수량·잔여 파렛트 반납까지 딸려와 상위 시스템 영역으로 번진다 |
| 파렛트 소터 사용 | 실재하는 설비이나 일반적이지 않다. 소터의 대표적 동작을 다루기 어렵다 |

### 근거
케이스로 통일하면 랙에서 슈트까지 **단위가 한 번도 바뀌지 않는다.**
설비를 늘리지 않고 문제가 사라지며, 소터가 케이스를 다루는 것이 실제 구성이므로 오히려 정확해진다.
미니로드 AS/RS는 케이스·토트 보관을 목적으로 하는 실제 제품군이다.

### 확장 지점
디팔레타이저(파렛트 → 케이스)는 **이 프로젝트 범위 밖의 확장 예시**로 둔다.
다만 나중에 설비를 추가할 때 기존 코드를 고치지 않아도 되도록, 다음 세 가지를 지킨다.

| 원칙 | 내용 |
|---|---|
| 경로를 데이터로 | 설비 순서를 조건문이 아니라 목록으로 표현한다. 설비 추가 = 목록에 한 줄 추가 |
| 이름에 단위를 박지 않음 | `palletNo`가 아니라 `loadId`. 케이스·파렛트·토트 어느 것이 와도 그대로 쓴다 |
| 상태 머신은 설비를 모름 | `TaskStatus`에 설비 종류를 넣지 않는다. 어느 설비든 같은 순서를 밟는다 |

**확장 지점을 하나로 한정한다.** 열어둔 것은 "설비가 늘어나는 것" 하나뿐이며,
그 외 항목을 미리 추상화하지 않는다.

### 영향
- 용어가 파렛트에서 케이스로 바뀐다 (`PLT-9001` → `CS-9001`)
- 설비 구성은 3종 유지. 신호 흐름 구조는 변경 없음
- 디팔레타이저·P&D 스테이션 승격은 같은 패턴의 반복이므로 언제든 추가 가능

## ADR-0009 · 진행 중 작업 수를 저장하지 않고 계산한다

### 결정
설비가 작업을 더 받을 수 있는지 판단할 때 쓰는 **진행 중 작업 수를 설비에 저장하지 않는다.**
작업 목록에서 그때그때 세어 `Equipment.canAccept(int)`에 넘긴다.

### 배경
설비마다 동시에 처리 가능한 수가 다르다. 스태커크레인은 포크가 하나라 1건이지만
컨베이어는 존마다, 소터는 캐리어마다 화물이 올라간다.
따라서 "지금 몇 건이 올라가 있는가"를 알아야 하달 여부를 정할 수 있다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 설비에 카운터 필드를 두고 하달 시 +1, 완료 시 −1 | 작업 상태와 이중 관리가 된다. 예외 경로에서 감소를 한 번 놓치면 그 설비는 영구히 "가득 참"으로 남는다 |
| 설비가 작업 목록을 직접 들고 계산 | 설비가 저장소를 알게 되어, 판정 하나를 확인하는 데 저장소가 필요해진다 |

### 근거
작업 상태(`SENT`/`ACKED`/`EXECUTING`)가 이미 "설비에 내려가 있음"을 뜻한다.
같은 사실을 카운터로 한 번 더 적으면 두 값이 어긋날 수 있고,
어긋났을 때 어느 쪽이 맞는지 판단할 근거가 없다.
세어내는 방식은 진실의 원천이 작업 목록 하나뿐이라 어긋날 수가 없다.

### 영향
- `Equipment`는 `capacity`만 갖는 값 객체가 된다. 저장소도 작업 목록도 모른다
- 계수 책임은 작업 목록을 다루는 계층으로 넘어간다
- 계수 비용이 생기지만, 설비 수가 수십 대 규모이므로 문제되지 않는다

## ADR-0010 · 담당 크레인을 위치 코드에서 도출한다

### 결정
위치 코드를 값 객체 `LocationCode`로 두고, 랙 주소에서 **담당 크레인 코드를 계산해 얻는다.**
`A-01-03-02` → `SC-A01`. 별도 매핑 표를 두지 않는다.

### 배경
출발지·목적지를 문자열로 다루면 형식이 맞는지 아무도 검사하지 않는다.
`A-1-3-2`와 `A-01-03-02`가 같은 자리인지도 알 수 없고,
"이 자리를 어느 크레인이 담당하는가"는 매번 다른 곳에서 판단하게 된다.

### 검토한 대안

기각한 것과 미룬 것을 구분한다. 미룬 항목은 나중에 다시 꺼낼 수 있다.

| 대안 | 판단 |
|---|---|
| 위치–크레인 매핑 표를 별도 관리 | **기각.** 주소 체계와 표가 어긋날 수 있고, 어긋나면 없는 통로로 작업이 나간다 |
| 랙과 스테이션을 별도 타입으로 분리 | **보류.** 작업의 출발지·목적지에는 둘 다 올 수 있어 지금 나누면 사용하는 쪽이 매번 분기해야 한다. 종류마다 갖는 데이터가 실제로 달라지면 그때 나눈다 |
| 형식이 틀리면 빈 값 반환 | **기각.** 호출한 쪽이 검사를 잊으면 존재하지 않는 자리로 크레인이 출발한다 |

### 근거
랙 주소에 이미 존과 통로가 들어 있고, 통로마다 크레인이 한 대 선다.
즉 담당 크레인은 주소가 정해지는 순간 함께 정해지는 값이지 따로 관리할 정보가 아니다.
형식 위반은 되돌릴 방법이 없으므로 생성 시점에 예외로 끊는다.

### 종류를 값으로 갖는다

종류를 불리언이 아니라 `LocationKind` 열거형으로 갖는다.
지금 필요한 것은 랙과 스테이션 둘뿐이지만, P&D 스테이션을 설비로 승격하거나
슈트를 별도로 다루게 되면 종류가 늘어난다.
불리언은 셋째 종류가 생기는 순간 `isStation() && !isChute()` 같은 조합으로 번진다.

`isRack()` · `isStation()` 은 남긴다. 버리는 것이 아니라
`kind() == LocationKind.STATION` 의 축약이며, 읽기 쉬운 쪽이 호출부에 남는 편이 낫다.
다만 **분기는 `kind()` 로 하고, 불리언은 단일 조건에서만 쓴다.**

### 타입으로 갈라칠 이음매

랙과 스테이션을 별도 타입(`sealed interface`)으로 나누는 방식은 기각이 아니라 미룬 것이다.
지금 나누면 출발지·목적지에 둘 다 올 수 있는 `EquipmentTask` 쪽이 매번 분기해야 해서 이르다.
나중에 종류마다 갖는 데이터가 실제로 달라지면 나눈다. 그때를 위해 두 가지를 지킨다.

| 원칙 | 내용 |
|---|---|
| 종류 판별은 `kind()` 로 | `instanceof` 나 코드 문자열 파싱으로 종류를 판단하지 않는다. 갈라칠 때 고칠 지점이 `kind()` 호출부로 한정된다 |
| 분기는 `switch` 식으로 | `switch (kind())` 는 종류가 늘면 컴파일러가 빠진 가지를 잡아준다. sealed 타입으로 바뀌어도 패턴 매칭 switch로 형태가 그대로 이어진다 |

### 형식

| 종류 | 예 | 구성 |
|---|---|---|
| 랙 | `A-01-03-02` | 존(문자 1) − 통로 − 열 − 단, 번호는 두 자리 고정 |
| 스테이션 | `PND-A01` `IND-01` `CHUTE-3` | 이름 − 번호. 좌표를 갖지 않는다 |

두 자리 고정으로 두는 이유는 문자열 정렬이 곧 물리적 순서가 되기 때문이다.
`A-1-10` 형식에서는 `A-1-10`이 `A-1-2`보다 앞에 온다.

### 영향
- 위치 형식 검사와 해석이 한곳에 모인다
- 크레인 지정 로직이 사라진다. 출발지 주소가 곧 담당 설비다
- 스테이션에 `craneCode()`를 호출하면 예외다. 스테이션은 어느 통로에도 속하지 않는다
